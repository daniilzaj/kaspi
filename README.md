# Каспи

Каспи — прототип единой клиентской платформы для управляющей компании торгового комплекса. Он принимает события от разных арендаторов, собирает общие профили, формирует аудитории для перехода между проектами и считает первые подтверждённые покупки после кампаний. Все суммы в интерфейсе — в рублях.

## Запуск

Нужен Go 1.26+ и компилятор C для SQLite-драйвера.

```bash
go run .
```

Откройте кабинет управляющей компании [http://127.0.0.1:8080](http://127.0.0.1:8080) или отдельный портал арендатора [http://127.0.0.1:8080/partner](http://127.0.0.1:8080/partner). При первом запуске создаётся `data/kaspi.db` с синтетическими данными трёх арендаторов. Базу можно разместить в другом месте через `KASPI_DB`, адрес сервера — через `KASPI_ADDR`. Команда `KASPI_SEED_SAMPLE=1 go run .` добавляет расширенный набор синтетических данных и завершается; после неё запустите сервер обычной командой. Повторное заполнение не создаёт дубликаты.

## Структура

- `main.go` — запуск сервера и маршруты HTTP.
- `schema.go` — схема SQLite и миграции.
- `model.go` — проверка событий и сопоставление профилей.
- `imports.go` и `connector.go` — загрузка файлов, приём событий и подключение внешних API.
- `profiles.go` и `audiences.go` — профили, сегменты и кампании.
- `sample_seed.go` — синтетические данные для локального запуска.
- `web/` — интерфейсы управляющей компании и арендатора.

Проверка:

```bash
go test ./...
```

## Контракт данных

CSV/XLSX содержит одну строку на событие. Обязательные поля: `customer_id`, `event_id`, `event_type`, `occurred_at`. Для идентификации нужен хотя бы один из `name`, `phone`, `email`. Остальные поля: `amount`, `consent`, `related_event_id`. Полный шаблон доступен в интерфейсе.

Типы событий: `purchase`, `visit`, `booking`, `topup`, `usage`, `refund`. `topup` не приравнивается к визиту. Возврат должен ссылаться через `related_event_id` на исходную покупку, быть на полную сумму и принадлежать тому же клиенту. События уникальны по паре `tenant_id` + `event_id`.

Новые события отправляются через `POST /api/events`:

```json
{
  "tenant_id": 2,
  "customer_id": "pos-42",
  "event_id": "receipt-981",
  "name": "Мария Белова",
  "phone": "+7 913 222-33-44",
  "email": "maria@example.test",
  "consent": true,
  "event_type": "purchase",
  "occurred_at": "2026-10-31T14:00:00+07:00",
  "amount": 1200
}
```

### Подключение внешнего API

В портале арендатора раскройте «Передавать данные через API»: укажите GET URL и путь к массиву событий внутри JSON (например, `data.events`). Для каждого поля укажите путь внутри одного объекта: `client.id`, `receipt.id` и т. п. Обязательны `customer_id`, `event_id`, `event_type`, `occurred_at` и хотя бы одно из имени, телефона или e-mail. При необходимости задайте имя и значение заголовка авторизации. Кнопка «Проверить ответ» получает образец, показывает ошибки схемы и **не загружает** события. После сохранения «Загрузить данные» импортирует максимум 1000 событий за один запрос; повторный запуск не создаёт дубликаты по `event_id`.

Локальные API: `POST /api/connectors/test` (проверка), `POST /api/connectors` (сохранение), `GET /api/connectors` (список), `POST /api/connectors/{id}/sync` (ручная синхронизация). Например:

```json
{
  "tenant_id": 2,
  "name": "Касса кафе",
  "url": "https://example.com/api/events",
  "array_path": "data.events",
  "auth_header": "Authorization",
  "auth_value": "Bearer TOKEN",
  "field_map": {
    "customer_id": "client.id",
    "event_id": "receipt.id",
    "event_type": "kind",
    "occurred_at": "created_at",
    "name": "client.name",
    "phone": "client.phone",
    "amount": "total",
    "consent": "client.consent"
  }
}
```

Ответ API должен быть JSON-массивом или содержать массив по указанному пути. Поддерживаются простые пути через точку. Если источник использует свои типы событий, укажите соответствия в интерфейсе, например `sale=purchase, return=refund`. В Каспи используются `purchase`, `visit`, `booking`, `topup`, `usage`, `refund`. Синхронизация запускается вручную.

## Как устроено сопоставление

Каспи сначала ищет ранее известный ID клиента внутри арендатора, затем совпадение e-mail при совместимом имени, затем совпадение телефона **и** имени. Один телефон с разными именами создаёт отдельные профили. Решение и способ сопоставления сохраняются в `identity_decisions`; эта внутренняя механика не загромождает экран маркетолога.

Это консервативная стратегия для MVP. Она снижает риск ложной склейки семьи, но может оставить дубли при ошибках в имени или смене контакта. Отсутствие покупки трактуется только как отсутствие записи в полученных данных, не как доказательство, что человек никогда не был у арендатора.

## Границы прототипа

Здесь есть работающий сквозной цикл данных и измерения результата. Обучаемую модель рекомендаций не добавляли без реальной истории и контрольной группы: на таких данных она выдавала бы не заслуживающие доверия оценки. Правило сегментации объяснимо, а подтверждённые исходы кампаний уже сохраняются для дальнейшего обучения и A/B-тестов.

Сервер по умолчанию слушает только `127.0.0.1`. Разделение кабинетов пока **интерфейсное**: арендатор выбирает проект без входа. Перед пилотом с настоящими персональными данными нужны аутентификация, права по проектам, управление согласиями, защищённое хранение ключей API, ограничение адресов для исходящих запросов, журнал доступа и согласованный порядок обмена данными с арендаторами. В текущем прототипе значения заголовков авторизации хранятся в SQLite и не возвращаются в списке подключений. Используйте только тестовые ключи и синтетические данные.
